Plan: Unified IBM pipeline and ibm_fez training dataset¶

Status legend: [ ] not started · [~] in progress · [x] done. Update the Progress log at the bottom whenever a phase moves.

Goal¶

Build a fresh, consistent training dataset on ibm_fez for the thesis: every row is one QPU job whose pre-runtime features and post-runtime targets were computed by the same code, from the exact circuit that ran and the chip state when it ran.

  • Algorithms (thesis scope): Fourier-based (QFT, PE), oracle-based (Grover, BV), entanglement-based (vTP, GHZ).

  • Additional: coin toss (noise floor), random volumetric (control group), Shor (known-failure anchor).

  • Shots: 1,024 per job.

  • Optimization level: 3 only (fixed seed_transpiler, ISA frozen at prepare).

  • Repetitions: 2 runs per config per window, on the same frozen ISA circuit.

  • Windows: 3 calibration windows on different days, so 6 jobs per config.

  • Legacy data: existing runs are kept untouched as a separate legacy set. They are not recovered, rewritten or mixed with the new dataset.

  • New data location: data/qpu/v2/ (schema-versioned).

  • Rigetti and IonQ come later through the same plan format.

* QuantumSpecificMetrics measured cost on the logical circuit: 1.3 s (3 q), 6 s (6 q), 74 s (8 q), 462 s (9 q). Compute once per config up to 8 qubits; above that, record as missing with reason size_limit (not zero).

vTP S-configs are dynamic (if_else); M1/M2 reject dynamic circuits, so group E is recorded as missing for them. All other groups are computed.

Reference vs success set. Each record stores two things:

  • reference stores the ideal noiseless output distribution. GHZ uses its two equally likely labels and BV uses the measured secret in Qiskit bit order, including above 12 measured bits. The generic statevector path supports up to 20 qubits and 12 measured bits. Dynamic circuits use noiseless Aer sampling (200k shots, reference_exact: false). Hellinger and TVD are computed against this distribution.

  • success_set: the labels accepted by the runner’s create_success_criteria (for example PE accepts ±1 around the phase peak). success_rate and DSR use it. Baselines report *_error = predicted 1 − P(success set) and *_tvd = predicted TVD to the ideal, so each is comparable with its target.

Where the groups live in a record:

  • A, B, C, E: artifacts/<stem>/prepared.json → payload.features

  • D: journal → submission_journal[i].hardware_at_execution and baselines_at_execution

  • F: journal → individual_results[i].targets; the legacy evaluate_result fields are kept alongside

  • G: journal and prepared.json top-level keys

Findings that motivate the redesign¶

Old pipeline (ibm_experiment_base.py + executor.run_ibm):

  1. Files are written only if the run completes (ibm_experiment_base.py:356); timeouts lose job/batch IDs (hence hard-coded get_timed_out_batches).

  2. Gate-error characterization re-transpiles without a seed (ibm_experiment_base.py:325); on FakeFez, 4 transpiles gave 2–4 distinct layouts, so it may not describe the circuit that ran.

  3. Calibration is device medians from backend.target, captured before submission, timestamped now(); no per-qubit data.

  4. QWARD metrics are computed on the logical circuit only.

  5. Post-run targets differ per runner (evaluate_result in each of 11 runners; none uses FidelityMetrics); Hellinger/TVD/DSR are added later by enrichment scripts.

  6. --recover assigns optimization level by job order; update script covers only Grover/QFT; campaign state is tracked in shell-script comments.

  7. docs/thesis-dataset-plan.md states per-job historical calibration is unavailable; job.properties() worked for all 10 bv-ibm-fez jobs.

Calibration campaign (bv_calibration_ibm.py) has the right lifecycle (freeze → submit → idempotent recover → run-time calibration) but bypasses the base class and has bugs (see Phase 1).

Measured on FakeFez (opt 2, seed 11; opt 2 and opt 3 gave the same 2Q count on 23 of 25 sampled configs, median ratio 1.0). Predicted error is M1; real ibm_fez error was 1.5–3× higher in BV runs. Keep circuits between “almost always succeeds” and “pure noise”.

Coin toss is not part of the campaign: GHZ and random volumetric already cover the noise floor. Its runner stays available, and the 4 pilot jobs already run (CT3, CT3-B25) stay on disk but are filtered out of the export.

Distribution of predicted M1 error across the 172 configs: 75 below 10%, 59 at 10–30%, 20 at 30–60%, 2 at 60–90%, 1 above 90% (Shor), 15 dynamic (no prediction). The three high-error entries (Grover S5, Shor M3, RV8-D8) are deliberate anchors for where output turns into noise.

QPU time. Measured on the 34 pilot jobs (IBM usage.quantum_seconds, whole seconds, 1,024 shots): 32 jobs billed 2 s (ISA depth 4–438, circuit duration 0–14 µs), the two Shor jobs billed 3 s (depth 4,640, 136 µs). A Batch’s usage in the dashboard is the sum of its jobs (4 jobs = 8 s, Shor’s 2 jobs = 6 s); the pilot used 62 s in total. The 250 µs rep delay dominates short circuits, so billing is almost flat in circuit size. campaign_matrix.qpu_seconds is fitted to those numbers (31 ns per layer plus 1.7 s fixed per job) and predicts ~12 min per window, ~35 min for all 1,032 jobs (≈ 2,100 s of the account’s 10,800 s). The earlier “30 min” figure was this same total; the dashboard figure per Batch is 6–8 s because each Batch holds 2–4 jobs, not a whole window. run_campaign.sh usage [window] reads the real numbers from IBM next to the saved per-job values.

Dashboard tags. Every job carries <algorithm> first (ghz, bv → bernstein-vazirani, phase-estimation, …), then cfg:<config>, campaign:<id>, w<window>, repeat-<n> and the run ID. In the IBM dashboard, filter the Jobs table by the algorithm tag. Jobs submitted before this change carry only <run id> and repeat-<n>.

Phases¶

Phase 1 — Fix calibration-campaign bugs (no QPU) ✅¶

  • Rename manifest recovery to recover_manifest; base recover_batch(batch_id, ...) is no longer shadowed.

  • Align alpha: prepare and analysis share CLAIMS_PER_RUN (7); records store claims_per_run. Archived records keep their frozen alpha.

  • prepare_batch: manifest existence, runs, run budget and config IDs validated before any record is written.

  • submit_batch: per-(campaign, window) limits; one _submitted_runs helper replaces the duplicated scan.

  • One capture_calibration per candidate in rank_layouts; one calibration read per Batch submission.

  • Tests for each fix (499 passing).

Phase 2 — Shared lifecycle qward/examples/papers/ibm_campaign.py (no QPU) ✅¶

  • Record/journal with hashes, atomic UTF-8 writes, JSON encoder (RecordStore, schema 2.0).

  • Prepare: transpile once with fixed seed (default opt 3, seed 11), store logical + ISA QPY, used-qubit calibration snapshot (device-wide record optional), config, reference, payload; status prepared. ALAP for static circuits; dynamic circuits (vTP S) transpiled unscheduled. Faulty qubits/edges rejected before archiving.

  • Submit: job mode for single records; one Batch per plan with seeded shuffle, run 1 of every config before run 2; IDs journaled immediately; submission_unknown on send failure, never retried.

  • Runtime-options hook get_runtime_options(config) merged onto defaults (replaces Shor monkey-patch once Shor is ported).

  • Recover by saved job ID, idempotent, never resubmits; skips completed jobs; refuses never-submitted records; after_job hook for run-time calibration (wired in Phase 3).

  • Multi-register counts joined like Aer ("last first", space separated), verified against Aer.

  • Plans/manifests with windows and run budgets; offline --plan-status.

  • Compact CLI summaries.

  • Base CLI: --prepare-plan/--submit-plan/--recover-plan/--plan-status, --prepare-only (with --config --backend), --submit-record, --recover-record. New records go to <algo>/data/qpu/v2/.

  • Legacy run() and --update/--recover unchanged for existing data.

  • Dynamic-circuit-safe circuit_hash(allow_dynamic=True); static hashes unchanged, so archived snapshots still verify.

  • Tests: tests/test_ibm_campaign.py (9) with FakeFez + mocked Runtime; local Aer dry run of a 3-config GHZ plan end to end. 508 passing.

  • Note: the BV calibration campaign still uses its own lifecycle; it moves onto ibm_campaign in Phase 4 (records stay readable).

Phase 3 — Shared feature/target extractor (no QPU) ✅¶

  • qward/examples/papers/dataset_features.py: groups A–F as functions; G comes from the record. A group that cannot be computed is {"available": false, "reason": ...}, never zeros.

  • Group B on the executed circuit: compact_isa keeps active qubits in physical order and drops delays (QWARD metrics fail on the 156-qubit ISA with a TranspileLayout); gate depth and 2Q count preserved.

  • Runner contract in IBMExperimentBase: configs, circuit, create_success_criteria; get_reference defaults to the exact ideal distribution; optional get_runtime_options, include_quantum_specific.

  • One shared FidelityMetrics + HistogramAssessment pass for targets; legacy evaluate_result fields kept additively. Multi-register labels flattened (FidelityMetrics returned 0 success with spaced labels).

  • QuantumSpecific ≤ 8 qubits and static only; otherwise explicit reason.

  • Group E missing for dynamic circuits; *_error vs success set and *_tvd vs ideal; works for multi-target references.

  • Group D at recovery from job.properties() (calibration in effect when the job ran) plus baselines re-predicted from it.

  • Removed the Halstead difficulty ≤ 1000 / effort ≤ 1e8 caps in StructuralMetricsSchema; transpiled Shor exceeded them.

  • Tests: tests/test_dataset_features.py (13); local Aer dry run of all 9 algorithms — every group present (vTP-S: QS and E missing by design). 521 passing.

Phase 4 — Port runners (no QPU) ✅¶

All runners inherit the lifecycle from IBMExperimentBase; each gets a FakeFez + noisy-Aer test (tests/test_runner_ports.py, 22 tests) that checks groups A–G are present.

  • GHZ, BV, QFT, PE, Grover, random volumetric, coin toss (biased distribution is the exact reference, not the success set)

  • vTP static (V) and dynamic (S): dynamic is transpiled unscheduled; group E is missing by design; control-flow ops (if_else) have no IBM error and are counted separately (uncalibrated_control_flow_ops), not treated as missing calibration.

  • Shor: get_runtime_options returns DD (XpXm) + gate twirling, recorded in the frozen record; the lifecycle enforces the same QPU-safe guard as the legacy run() (simulator-only configs are refused). The executor monkey-patch stays only on the legacy path.

  • BV calibration campaign: shares write_json/json_value/now with ibm_campaign; its own lifecycle (prediction-specific records, M1/M2 assessment) stays for now and keeps reading bv-ibm-fez-1/2/3. Fully merging it into RecordStore is deferred: it adds nothing to the dataset and risks the archived records.

  • BV signal-background (27–29 qubits): no tractable ideal (more than 12 measured bits), so get_reference returns None; targets and baselines are {"available": false, "reason": "no_reference"}. Not part of the ibm_fez matrix.

  • Output: ideal_reference refuses circuits above 12 measured bits instead of enumerating them.

Phase 5 — Exporter and driver (no QPU) ✅¶

  • qward/examples/papers/dataset_export.py: one row per completed job, groups A–G flattened into prefixed columns (meta, config, a–f, e_exec, g); ~450 columns. Also derives f.observed_error and f.residual_vs_<model>, and queue/run seconds from IBM timestamps.

  • Output: dataset-*.csv, dataset_manifest.json, schema.json (column → group, dtype, non-null), export_report.json (skipped records, errors, warnings).

  • Validation fails the export (override: --allow-incomplete) on: no rows, duplicate job IDs, mixed/unexpected record schema, simulated backends (override: --allow-fake, tests only), unavailable group a/b/c/d/f, e missing without a documented reason, counts ≠ shots, coverage < 1. Warnings: undocumented QuantumSpecific gaps, calibration changed between prepare and execution, sampled references.

  • Reads only <algo>/data/qpu/v2/; legacy files and the legacy CSV pipeline are untouched. Prepared-but-unsubmitted records are skipped and reported.

  • docs/ibm_fez_dataset_schema.md: column groups, documented reasons for missing values, how to compare predictions with targets, plan-file format.

  • qward/examples/papers/run_campaign.sh: prepare | submit | recover |     status | export per algorithm and window. Credentials come from .env or the environment (nothing on the command line); submit asks for confirmation and is the only action that sends jobs; status is offline.

  • Tests: tests/test_dataset_export.py (10); 553 passing overall.

Phase 6 — Campaign plan files (no QPU) ✅¶

  • qward/examples/papers/campaign_matrix.py holds the selection as data, validates it against every runner’s config registry, and writes the plans: uv run -m qward.examples.papers.campaign_matrix --write (refuses to overwrite a plan that already has a manifest).

  • 32 plan files (8 algorithms × windows 0–3), <algo>/plans/<algo>-w<N>.json: campaign fez-dataset-v2, ibm_fez, 1,024 shots, optimization level 3, seed 11, 2 runs per config, distinct seeded order per plan, run budget = configs × 2.

  • One Batch per algorithm per window; seeded shuffle of configs, run 1 of every config before run 2 (job_order in the manifest).

  • Job counts and QPU estimate per window: see the table above; campaign_matrix --report reproduces them locally.

  • QuantumSpecificMetrics seeded (torch seed 11, RNG state restored): it optimizes from random starts, so two computations of the same circuit differed. Features are now reproducible.

  • QuantumSpecific eligibility in the current matrix: 123 configs (static, ≤ 8 qubits). The original timing sweep took 23.8 min with a cold cache (60–80 s per 8-qubit circuit). The cache key includes the logical circuit, its expansion into primitive gates, seed, metric source and torch version. The cache lives under qward/examples/papers/data/quantum_specific_cache/. campaign_matrix --precompute-quantum-specific fills it once (~24 min); afterwards every prepare is a cache hit and the three windows share the same values. Tests never touch the repository cache.

  • Tests: tests/test_campaign_matrix.py (18): configs exist, sizes, anchors and cuts, files on disk equal the generator output, every plan passes prepare_plan validation, driver paths match.

  • User approval of the matrix before any QPU use.

Phase 7 — Pilot (QPU) ✅ run, ✅ export clean¶

  • 1 small + 1 mid config per algorithm, opt 3, 2 runs each; Shor anchor once. 30 jobs for the 8 campaign algorithms (the 4 coin-toss jobs run before it was dropped stay on disk, excluded from the export).

  • Prepared, submitted one Batch at a time, recovered; all 9 manifests completed, no job errors.

  • Export of the real data: 30 rows, 0 errors. Warnings: 2 sampled references (the dynamic vTP config, by design) and 4 QuantumSpecific failures on PE-S6 and SP6-P4 (see Findings).

  • Findings:

    • IBM advanced its calibration timestamp 2–3 times between prepare and execution, but the values of the qubits used did not change in any of the 17 records. The notice is now one line per submission, and group D has changed_values (compares what the circuit depends on); the export warns only when values change.

    • QuantumSpecificMetrics gave NaN coherence on PE-S6 and SP6-P4: torch.abs backpropagates NaN through exactly-zero off-diagonals of structured unitaries (first at step 120 of 300). Fixed with an exact zero-safe absolute value; values elsewhere are unchanged.

    • IBM limits active Batches. The driver tracks queued and running jobs and can resume from their manifest IDs.

  • Re-run prepare for PE-S6 and SP6-P4 features if the pilot data is kept (their a.quantum_specific is unavailable in those 4 rows).

To repeat the 30-job pilot, use a fresh label such as 0-r2. It copies the original plans and order into campaign fez-dataset-v2-pilot-r2, window 0. The original pilot and the new repeat have separate manifests and run budgets.

campaign=qward/examples/papers/run_campaign.sh
"$campaign" prepare all 0-r2
"$campaign" status "" 0-r2
"$campaign" submit all 0-r2 --max-batches 2
"$campaign" usage 0-r2

Expect eight prepared manifests and 30 planned jobs before confirming submission. Reuse the same label to resume. A fresh repeat uses the next label, e.g. 0-r3. After export, select this repeat by its meta.campaign_id.

Phase 8 — Full campaign (QPU)¶

  • Window 1, all algorithms.

  • Window 2 (different day).

  • Window 3 (different day).

  • Final export and data description.

From the repository root, prepare window 1 shortly before submitting it. To move the QuantumSpecific compute time ahead of calibration capture, first run uv run -m qward.examples.papers.campaign_matrix --precompute-quantum-specific.

campaign=qward/examples/papers/run_campaign.sh
"$campaign" prepare all 1
"$campaign" status "" 1

For a fresh window the status should show eight prepared manifests, 344 jobs planned in total and zero submitted. If preparation was interrupted, prepare the individual algorithms that still lack manifests.

"$campaign" submit all 1
"$campaign" status "" 1
"$campaign" usage 1
"$campaign" export

submit all defaults to two active Batches in the selected window. Use --max-batches 1, 2 or 3 to change the limit. Queued jobs occupy a slot until the Batch finishes and its results are recovered. On restart, previously submitted Batches count toward the limit. Other windows and independent submissions can also occupy IBM account slots. At completion expect eight completed manifests and 344 submitted jobs. The default export is qward/examples/papers/dataset_out/dataset-*.csv, with ordered parts listed in dataset_manifest.json (at most 20 MB per file). Filter to window 1 to check its coverage separately from the 30 retained pilot jobs.

import json
from pathlib import Path
import pandas as pd

folder = Path("qward/examples/papers/dataset_out")
manifest = json.loads((folder / "dataset_manifest.json").read_text())
data = pd.concat([pd.read_csv(folder / part["file"]) for part in manifest["parts"]], ignore_index=True)
w1 = data[(data["meta.backend_name"] == "ibm_fez")
          & (data["meta.campaign_id"] == "fez-dataset-v2")
          & (data["meta.window"] == 1)]
pairs = w1.groupby(["meta.algorithm", "meta.config_id"])["meta.run_index"].agg(set)
assert len(w1) == w1["meta.job_id"].nunique() == 344
assert len(pairs) == 172 and all(indices == {0, 1} for indices in pairs)

For the monthly dashboard, filter by backend, campaign and window. Window 0 is the pilot. In QFT PV4-P8, the ±1 tolerance accepts all 16 labels, so use TVD to measure performance. The SP and PV variants at (qubits, period) = (4, 2), (4, 4), (6, 4) and (6, 8) are identical logical circuits. Keep their job rows and group each pair together when estimating a size limit.
